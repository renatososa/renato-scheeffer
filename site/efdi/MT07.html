Módulo Técnico 7: interfaces

En este módulo trabajamos sobre interfaces de control para sistemas embebidos y sobre la relación entre el usuario, el hardware y la lógica interna del microcontrolador. La idea general fue entender que una interfaz no es solamente una capa visual, sino una mediación concreta entre las acciones del usuario y el comportamiento del sistema físico. En ese sentido, también resultó importante pensar qué información conviene mostrar, qué controles tienen más sentido para cada actuador y cuál es el modelo mental más claro para operar el dispositivo sin perderse en su complejidad interna.

La tarea propuesta para este módulo consistió en diseñar e implementar una interfaz de control para operar uno o más actuadores conectados a un ESP32.

Propuesta implementada

Para resolver esta consigna decidí implementar una interfaz web servida directamente por el ESP32, siguiendo una lógica bastante cercana a la utilizada en el módulo anterior pero aplicada ahora al control de actuadores mediante una página accesible desde el navegador. Los actuadores elegidos fueron un motor paso a paso NEMA 17 controlado a través de un A4988 y un LED RGB. Desde la interfaz el usuario puede indicar velocidad, cantidad de rotaciones y sentido de giro del motor, y además modificar el color y el brillo del LED o apagarlo por completo.

La comunicación entre la interfaz y el ESP32 se resuelve mediante un servidor HTTP embebido. La propia placa sirve la página web y recibe las órdenes a través de distintas rutas como /motor, /rgb y /off. De esta manera el navegador actúa como cliente y el ESP32 como servidor, sin necesidad de software adicional en la computadora para operar el sistema.

Implementación del sistema en simulación

La primera etapa del trabajo consistió en implementar el sistema completo en simulación. En este caso se montó un ESP32 conectado a un A4988, un motor paso a paso y un LED RGB. La idea fue validar primero la lógica general de la interfaz y del control de actuadores antes de pasar al hardware real. A diferencia del módulo 6, aquí no se trató de comunicar dos nodos por red, sino de hacer que un mismo ESP32 recibiera órdenes desde una interfaz web y las transformara en acciones físicas sobre el motor y el LED.

En este primer bloque se incorporan las librerías necesarias para conectividad y servidor web, se define la conexión a la red de Wokwi y se establecen los pines utilizados para cada actuador. El motor paso a paso se controla con tres señales del driver A4988: dirección, paso y habilitación. Por otro lado, el LED RGB utiliza tres salidas independientes para controlar sus canales rojo, verde y azul.

Control del motor paso a paso
float currentPositionRotations() {
  return static_cast<float>(motorPositionSteps) / STEPS_PER_REV;
}

uint16_t rpmToStepsPerSec(uint16_t rpm) {
  return static_cast<uint16_t>((static_cast<uint32_t>(rpm) * STEPS_PER_REV) / 60.0f);
}

void setMotorDirection(bool clockwise) {
  motorDirectionCw = clockwise;
  digitalWrite(DIR_PIN, clockwise ? HIGH : LOW);
}

void enableDriver() {
  digitalWrite(ENABLE_PIN, LOW);
}

void pulseStep(uint32_t halfPeriodUs) {
  digitalWrite(STEP_PIN, HIGH);
  delayMicroseconds(halfPeriodUs);
  digitalWrite(STEP_PIN, LOW);
  delayMicroseconds(halfPeriodUs);
}

void moveMotorRotations(float rotations, bool clockwise, uint16_t speedRpm) {
  const long steps = lroundf(rotations * STEPS_PER_REV);
  const uint16_t speedStepsPerSec = rpmToStepsPerSec(speedRpm);
  const uint32_t halfPeriodUs = max<uint32_t>(150, 500000UL / speedStepsPerSec);

  setMotorDirection(clockwise);
  enableDriver();

  for (long i = 0; i < steps; ++i) {
    pulseStep(halfPeriodUs);
  }

  motorPositionSteps += clockwise ? steps : -steps;
}

Este bloque concentra la lógica principal del motor. Primero se convierten las revoluciones por minuto a pasos por segundo y luego se calcula el período necesario entre pulsos para obtener la velocidad deseada. La función moveMotorRotations() es la encargada de fijar el sentido de giro, habilitar el driver y generar la cantidad de pulsos correspondiente a las rotaciones solicitadas por el usuario. Además, se mantiene una variable interna con la posición acumulada del motor expresada en pasos para poder mostrar esa información en la interfaz.

Control del LED RGB
String rgbToHex(uint8_t red, uint8_t green, uint8_t blue) {
  char buffer[8];
  snprintf(buffer, sizeof(buffer), "#%02X%02X%02X", red, green, blue);
  return String(buffer);
}

void applyLedFromSelection() {
  currentRed = static_cast<uint8_t>((static_cast<uint16_t>(baseRed) * currentBrightnessPct) / 100);
  currentGreen = static_cast<uint8_t>((static_cast<uint16_t>(baseGreen) * currentBrightnessPct) / 100);
  currentBlue = static_cast<uint8_t>((static_cast<uint16_t>(baseBlue) * currentBrightnessPct) / 100);

  ledcWrite(LED_R_PIN, currentRed);
  ledcWrite(LED_G_PIN, currentGreen);
  ledcWrite(LED_B_PIN, currentBlue);
}

void setLedOff() {
  currentBrightnessPct = 0;
  applyLedFromSelection();
}

bool parseHexColor(const String& value, uint8_t& red, uint8_t& green, uint8_t& blue) {
  String hex = value;
  if (hex.startsWith("#")) {
    hex.remove(0, 1);
  }

  if (hex.length() != 6) {
    return false;
  }

  const long number = strtol(hex.c_str(), nullptr, 16);
  red = static_cast<uint8_t>((number >> 16) & 0xFF);
  green = static_cast<uint8_t>((number >> 8) & 0xFF);
  blue = static_cast<uint8_t>(number & 0xFF);
  return true;
}

Para el LED RGB se implementó una lógica sencilla pero bastante flexible. La interfaz le permite al usuario elegir un color en formato hexadecimal y un porcentaje de brillo. La función parseHexColor() convierte el valor elegido a sus componentes rojo, verde y azul, mientras que applyLedFromSelection() aplica además el brillo seleccionado y actualiza los tres canales mediante PWM. La función setLedOff() permite apagar el LED sin perder el color base previamente seleccionado.

Interfaz web y recepción de órdenes

Uno de los aspectos más importantes de esta práctica fue la propia interfaz. La página servida por el ESP32 muestra al usuario el estado actual del sistema y ofrece controles claros para actuar sobre cada uno de los actuadores. En la parte superior se presenta la posición actual del motor en rotaciones y el color que está mostrando el LED. Luego la interfaz se divide en dos áreas principales: una dedicada al motor y otra al LED RGB.

En la sección del motor el usuario puede modificar la velocidad mediante un control deslizante, indicar la cantidad de rotaciones y elegir el sentido de giro entre horario y antihorario. En la sección del LED el usuario puede elegir un color, ajustar el brillo y apagar completamente el actuador. De esta forma la interfaz no solo permite mandar órdenes, sino también mantener una referencia bastante clara del estado del sistema.

void handleMotor() {
  const uint16_t speedRpm = static_cast<uint16_t>(
    readIntArg("speed", DEFAULT_SPEED_RPM, MIN_SPEED_RPM, MAX_SPEED_RPM)
  );
  const float rotations = readFloatArg("rotations", DEFAULT_ROTATIONS, MIN_ROTATIONS, MAX_ROTATIONS);
  const bool clockwise = server.arg("dir") != "ccw";

  moveMotorRotations(rotations, clockwise, speedRpm);
  currentSpeedRpm = speedRpm;
  redirectHome();
}

void handleRgb() {
  uint8_t selectedRed = baseRed;
  uint8_t selectedGreen = baseGreen;
  uint8_t selectedBlue = baseBlue;

  if (server.hasArg("color")) {
    parseHexColor(server.arg("color"), selectedRed, selectedGreen, selectedBlue);
  }

  baseRed = selectedRed;
  baseGreen = selectedGreen;
  baseBlue = selectedBlue;
  currentBrightnessPct = static_cast<uint8_t>(readIntArg("brightness", currentBrightnessPct, 0, 100));
  applyLedFromSelection();
  redirectHome();
}

En este caso la propia página HTML contiene formularios que envían datos al ESP32 mediante peticiones HTTP. Cuando el usuario presiona los botones de la interfaz, el servidor recibe los parámetros correspondientes y ejecuta la función asociada a cada ruta. De esta forma, la interfaz y la lógica de control quedan estrechamente integradas dentro del mismo firmware.

Inicialización del servidor y rutina principal
void connectWiFi() {
  if (WiFi.status() == WL_CONNECTED) {
    return;
  }

  WiFi.mode(WIFI_STA);
  WiFi.begin(WIFI_SSID, WIFI_PASSWORD);

  while (WiFi.status() != WL_CONNECTED) {
    delay(250);
  }
}

void setupServer() {
  server.on("/", handleRoot);
  server.on("/motor", handleMotor);
  server.on("/rgb", handleRgb);
  server.on("/off", handleOff);
  server.on("/status", handleStatus);
  server.onNotFound(handleRoot);
  server.begin();
}

void setup() {
  Serial.begin(115200);
  setupStepper();
  setupRgb();
  connectWiFi();
  setupServer();
}

void loop() {
  if (WiFi.status() != WL_CONNECTED) {
    connectWiFi();
  }

  server.handleClient();
  delay(2);
}

Finalmente se inicializan el motor, el LED y la conexión de red, para luego poner en marcha el servidor HTTP. Dentro del loop() el ESP32 queda atendiendo continuamente al navegador y procesando las órdenes que llegan desde la interfaz. En este caso no se necesita un protocolo adicional como MQTT, ya que toda la interacción ocurre de forma directa entre el navegador y el microcontrolador.

Acceso al servidor simulado desde la PC

Para la simulación del sistema se utilizó la misma plataforma embebida en Visual Studio Code que en el módulo 6. Sin embargo, en este caso apareció un requerimiento adicional: como el objetivo era probar una interfaz web servida por el propio ESP32, fue necesario implementar un bridge de red que permitiera acceder desde la computadora al servidor HTTP que corría dentro del entorno simulado.

Esta configuración se resolvió mediante el archivo wokwi.toml, que redirige el puerto local 8180 hacia el puerto 80 del ESP32 simulado. De esta forma, la interfaz se puede abrir desde el navegador de la PC utilizando la dirección http://localhost:8180. 

[wokwi]
version = 1
firmware = ".build/server.ino.bin"
elf = ".build/server.ino.elf"

[[net.forward]]

to = "target:80"

Implementación real

Una vez validada la lógica general del sistema en simulación se realizó la implementación sobre hardware real. En esta etapa se mantuvo el mismo enfoque general: un único ESP32 sirviendo una interfaz web y controlando un motor paso a paso junto con un LED RGB. Sin embargo, aparecieron varias diferencias prácticas vinculadas al montaje físico, la alimentación del driver y el cableado real del motor.

Configuración real del servidor y de los pines
#include <WiFi.h>
#include <WebServer.h>

const char* AP_SSID = "MT07";

constexpr uint8_t DIR_PIN = 26;
constexpr uint8_t STEP_PIN = 27;
constexpr uint8_t ENABLE_PIN = 14;

constexpr uint8_t LED_B_PIN = 25;
constexpr uint8_t LED_G_PIN = 33;
constexpr uint8_t LED_R_PIN = 32;

WebServer server(80);

En la implementación real se modificó la configuración de red respecto a la simulación para que el propio ESP32 funcionara como punto de acceso. De esta manera la interfaz puede abrirse conectándose directamente a la red generada por la placa, sin depender de la red local de la casa ni de un bridge adicional. También se ajustó la asignación de pines para acomodarla al montaje físico definitivo del sistema. 

void setupAccessPoint() {
  WiFi.mode(WIFI_AP);
  if (!WiFi.softAP(AP_SSID)) {
    Serial.println("No se pudo iniciar el punto de acceso");
    return;
  }

  Serial.println();
  Serial.print("WiFi: ");
  Serial.println(AP_SSID);
  Serial.print("IP: ");
  Serial.println(WiFi.softAPIP());
}

Esta modificación permite acceder a la interfaz conectándose al WiFi generado por el ESP32 y entrando luego a la dirección que informa el propio sistema por el puerto serial. En este caso la lógica de control de actuadores no cambia, pero sí la forma en que el usuario establece la conexión inicial con el servidor.

Alimentación del driver y conexiones del motor real

Una diferencia importante entre simulación e implementación real es que en Wokwi no fue necesario alimentar al driver del motor con una fuente de potencia externa. En la práctica real esto sí resultó indispensable. Para poder mover el motor paso a paso se utilizó una fuente de 24 V y 2 A conectada al A4988, ya que la alimentación lógica del ESP32 no es suficiente para resolver por sí sola la etapa de potencia del actuador.

Además, durante el montaje apareció otra dificultad concreta: el motor utilizado en la implementación real fue un NEMA17HS de 6 pines, mientras que en la simulación se trabajó con una representación simplificada de cuatro terminales. Por este motivo la correspondencia de conexiones no fue exactamente la misma. En la simulación las bobinas aparecen directamente como A1 A2 B1 B2, mientras que en el motor real la disposición observada fue B1 X A1 B2 X A2, donde X representa terminales sin conexión en este montaje. Esto obligó a identificar correctamente cada bobina antes de conectarla al driver para evitar un comportamiento errático del motor.

Funcionamiento general del sistema real

Más allá de estas adaptaciones, el comportamiento general del sistema se mantuvo coherente con lo validado previamente en simulación. La interfaz siguió permitiendo setear la velocidad, las rotaciones y el sentido de giro del motor, así como cambiar el color y el brillo del LED RGB. Lo que cambió fue el contexto de implementación: la presencia de una fuente externa para el driver, un cableado real del motor más complejo y la necesidad de ajustar la configuración de red para que el sistema pudiera operar de forma autónoma.

Conclusiones

Esta práctica permitió implementar una interfaz de control clara y funcional sobre un ESP32, integrando una capa web con el accionamiento directo de un motor paso a paso y un LED RGB. El resultado fue interesante porque permitió trabajar al mismo tiempo sobre la interfaz, la lógica embebida y el comportamiento físico de los actuadores.

También quedó bastante claro que el pasaje de simulación a hardware real introduce dificultades que no siempre se hacen evidentes en el entorno virtual. En este caso eso se vio sobre todo en la alimentación del driver y en el cableado del motor de 6 pines. Aun así, la simulación resultó muy útil para validar la arquitectura general del sistema y la lógica de interacción antes de enfrentar esas complejidades en el montaje físico.

El código correspondiente a la implementación real de este sistema se puede encontrar en el repositorio, en el archivo server.ino.
